# Database Guidelines & Migration Verification

All database changes must be managed via Prisma migrations. Never edit the
database schema by hand, and never edit a migration after it has been merged.

## Migration Verification Requirements

`scripts/verify-migrations.sh` (`npm run db:verify`) enforces the rules below.
CI runs it in the `verify-migrations` job on every pull request and push to
`main`, with full git history and a disposable PostgreSQL database, so the
static, history and replay tiers all run there. Locally, the history and replay
tiers run when you opt in through the environment variables shown.

### 1. Structure and SQL (always)

- `prisma/schema.prisma` passes `prisma validate`.
- `prisma/migrations/migration_lock.toml` is committed and its `provider`
  matches the schema's datasource provider.
- Every migration lives in its own folder named
  `<YYYYMMDDHHMMSS>_<snake_case_name>` (as generated by `prisma migrate dev`).
  The only exception is a `0_<name>` baseline, which sorts first. Two folders
  may not share a timestamp.
- Every folder contains a `migration.sql` with at least one statement. No other
  files are allowed at the top of `prisma/migrations/`.
- Every `migration.sql` is lexically well formed: no merge-conflict markers,
  balanced parentheses, terminated strings, identifiers and comments, and a
  final statement that ends with `;`. Comments, quoted strings and
  dollar-quoted function bodies are understood, so punctuation inside them is
  not flagged.
- A migration folder must not contain leftovers of an interrupted merge
  (`*.orig`, `*.rej`, `*.bak`, `*~`) or a file with unresolved conflict
  markers. Prisma only applies `migration.sql`, so such a file can silently
  replace the real content of the migration.

Statements are classified as a whole, not line by line, so a multi-line
statement is judged as one statement.

#### Forbidden statements (never allowed)

`DROP DATABASE`, `DROP SCHEMA`, role and privilege management
(`CREATE`/`ALTER`/`DROP ROLE|USER|GROUP`, `GRANT`, `REVOKE`), `ALTER SYSTEM`,
`pg_terminate_backend`, `pg_cancel_backend`, `REASSIGN OWNED` and
`COPY ... PROGRAM` fail the run. They must never appear in an application
migration, not even with an opt-in.

#### Destructive statements (rejected unless the migration opts in)

`DROP TABLE`/`COLUMN`/`TYPE`/`VIEW`/`INDEX`/…, `TRUNCATE`, `DELETE FROM`,
`UPDATE` without `WHERE`, column type changes, `SET NOT NULL` and renames
**fail the run**. A migration that needs one has to say so explicitly:

```sql
-- astroid:allow-destructive the column is unused and holds no data
ALTER TABLE "Thing" DROP COLUMN "name";
```

The opt-in is per file and applies to the whole file; the reason after the
marker is required to be readable by the reviewer. `ALLOW_DESTRUCTIVE_MIGRATIONS=true`
accepts every destructive statement, which is useful locally but must not be
used in CI. A migration that is already merged cannot be changed any more, so
a destructive statement in one is only reported as a warning.

#### Unsafe statements (rejected)

- `ADD COLUMN ... NOT NULL` without a `DEFAULT` fails as soon as the table
  holds rows. Add a `DEFAULT`, or add the column as nullable and backfill it
  in a second migration. A column that is added to a table created by the same
  migration is fine.
- `CREATE INDEX CONCURRENTLY` must be the only statement of its migration
  (PostgreSQL refuses it inside a transaction block, and Prisma sends a
  multi-statement migration as one) and must not use `IF NOT EXISTS` (a failed
  concurrent build leaves an invalid index behind). See
  [`concurrent-indexes.md`](concurrent-indexes.md).
- An index that is created without `CONCURRENTLY` on a table that is not
  created by the same migration is reported as a warning: on a live table it
  blocks writes.

### 2. History (`MIGRATION_BASE_REF`)

```bash
MIGRATION_BASE_REF=origin/main npm run db:verify
```

- Migrations that already exist on the base branch must not be modified or
  deleted. Deployed databases store a checksum for every applied migration, so
  any edit breaks `prisma migrate deploy`. Add a new migration instead.
- New migrations must sort after the newest migration on the base branch. If
  another migration was merged first, regenerate yours with a current timestamp.
- The index advisories are only reported for migrations that are new relative
  to the base branch; the ones already merged cannot be changed any more.

### 3. Replay and drift (`SHADOW_DATABASE_URL`)

```bash
SHADOW_DATABASE_URL=postgresql://postgres:password@localhost:5432/astroid_shadow npm run db:verify
```

> The shadow database is **reset**. Never point this at a database whose data
> you need.

- The full migration history is replayed in order on the empty database. This
  catches invalid SQL and migrations that depend on objects created by a later
  migration.
- The replayed schema is compared with `prisma/schema.prisma`. Any difference
  means a schema change was committed without its migration; generate one with
  `npx prisma migrate dev --name <change>`.

### 4. Working tree (`CHECK_GIT_DIRTY`)

```bash
CHECK_GIT_DIRTY=true npm run db:verify
```

Fails when the working tree contains uncommitted schema or migration changes.

## Reading failures

Each problem is reported with the file (and line, where applicable) and the
fix to apply. All problems are reported in one run; in CI they also appear as
annotations on the pull request diff. The script exits non-zero if any error
was found. Warnings never fail the run.
All database changes must be managed via Prisma migrations.

## Startup Checks

The API retries PostgreSQL connections during startup using exponential backoff. Configure the total number of attempts with `DATABASE_CONNECT_RETRY_ATTEMPTS` (default `5`) and the initial delay with `DATABASE_CONNECT_RETRY_DELAY_MS` (default `1000` ms). Startup fails if either Prisma pool cannot connect or if any checked-in migration is pending or failed; deploy migrations before starting the API.

## Migration Verification Requirements

- Every migration folder must contain a valid, non-empty `migration.sql` file.
- Migration directories must start with a 14-digit timestamp prefix (`YYYYMMDDHHMMSS`) to ensure strict ordering and avoid conflicts.
- Run `npm run db:verify` locally to execute `scripts/verify-migrations.sh` prior to opening a pull request.
- The CI pipeline automatically runs `scripts/verify-migrations.sh` to validate schema syntax, migration structure, and working tree cleanliness.

## Startup Migration Check
Before the HTTP server starts listening, `main.ts` calls `PrismaService.verifyMigrations()`, which compares the folders in `prisma/migrations` with the rows in `_prisma_migrations` (rolled-back rows are ignored). The behaviour is controlled by `DATABASE_MIGRATION_CHECK`:

| Mode | Default for | Pending or failed migrations | Migration history unreadable (e.g. DB down) |
|------|-------------|------------------------------|---------------------------------------------|
| `strict` | `NODE_ENV=production` | Logs the offending migrations with remediation steps and aborts startup (exit code 1) | Aborts startup |
| `warn` | every other environment | Logs the same instructions and keeps booting | Logs a warning and keeps booting |
| `off` | never | Check skipped | Check skipped |

To recover from an aborted start:
- Pending migrations: run `npm run prisma:deploy` against the target `DATABASE_URL`, then restart the service.
- Failed migrations: inspect the `logs` column in `_prisma_migrations`, repair the database, run `npx prisma migrate resolve --rolled-back <name>` (or `--applied <name>`), then redeploy.

If the runtime image keeps migrations somewhere other than `<cwd>/prisma/migrations`, point `DATABASE_MIGRATIONS_DIR` at that folder. When no migrations are found on disk, the check logs a warning instead of silently passing.
## Migration CLI and Rollback Protection

`npm run db:migrate -- <command>` wraps the Prisma migration commands behind a production safety guard (`src/database/migration-guard.ts`).

| Command | Effect | Destructive |
| --- | --- | --- |
| `deploy` | Applies pending migrations (`prisma migrate deploy`). | No |
| `status` | Reports applied and pending migrations. | No |
| `down <migration>` | Executes the migration's `down.sql`, then removes it from `_prisma_migrations` in the same script so `deploy` can re-apply it later. | Yes |
| `reset` | Drops and recreates the database (`prisma migrate reset`). | Yes |

Destructive commands are **rejected when `NODE_ENV=production`**: the CLI prints a warning to stderr, exits with code `1`, and never contacts the database. To proceed intentionally, take a verified backup and re-run with `--force`; the override itself is also announced on stderr.

```bash
# Blocked in production
NODE_ENV=production npm run db:migrate -- down 20260901080000_add_cleanup_job_logs

# Explicit override
NODE_ENV=production npm run db:migrate -- down 20260901080000_add_cleanup_job_logs --force
```

Prisma does not generate down migrations. To make a migration reversible, add a hand-written `down.sql` next to its `migration.sql`. One way to draft it is to run the following after editing `schema.prisma` but **before** applying the new migration, so the diff goes from the new datamodel back to the current database state:

```bash
npx prisma migrate diff   --from-schema-datamodel prisma/schema.prisma   --to-schema-datasource prisma/schema.prisma   --script > prisma/migrations/<migration>/down.sql
```

Review the generated SQL by hand before relying on it. `down` refuses to run for a migration without a `down.sql`.

## Migration verification CI troubleshooting (#437)

The `verify-migrations` job in `.github/workflows/ci.yml` runs `npm run db:verify` against a **disposable** PostgreSQL service. It sets `MIGRATION_BASE_REF` to compare committed migration history and `SHADOW_DATABASE_URL` for migration replay and schema-drift checks. **Never point `SHADOW_DATABASE_URL` at a database containing valuable data**: the verification script resets it.

For a local reproduction, start an isolated PostgreSQL database, install dependencies, and run:

```bash
npm ci
MIGRATION_BASE_REF=origin/main \
SHADOW_DATABASE_URL='postgresql://postgres:password@localhost:5432/astroid_shadow?schema=public' \
npm run db:verify
```

If verification fails, inspect the first reported error and follow the corresponding action:

- **Prisma connection failure:** confirm PostgreSQL is running, the supplied credentials and database name are correct, and the database is disposable.
- **Unapplied or failing migration:** review the failing `prisma/migrations/<migration>/migration.sql`, correct it in a new migration if already deployed, and rerun verification against a fresh disposable database.
- **Schema drift:** generate and review a Prisma migration for the intended `schema.prisma` change; do not silently bypass the drift check.
- **Migration-history mismatch:** restore any migration already merged to `main` and add a forward migration instead of rewriting published history.

A run without `SHADOW_DATABASE_URL` performs only the applicable static/history checks; it **does not** prove that migrations replay successfully or that the database schema has no drift.
